# discovery：提断言

从攻击者的视角读代码：不是"哪里写得不好"，而是"攻击者能让程序做什么它不该做的事"。

## 找入口

- 接受外部输入的地方：HTTP 路由、WebSocket、消息队列、文件上传、命令行参数、环境变量、数据库里来自用户的字段、第三方回调。
- 行使权限的地方：认证中间件、授权检查、租户隔离、管理员接口。
- 敏感操作：执行命令、拼 SQL、渲染模板、反序列化、文件路径拼接、发请求、写日志、返回错误页。

## 跟数据流

对每个入口，跟着输入走：经过哪些变换（解析、拼接、编码）、经过哪些控制（校验、转义、鉴权）、最后到了哪个敏感操作。链路上任何一处缺了控制，就是候选断言；证据就是链上的定位。

## 什么算候选

- 能说出"攻击者做什么 → 程序发生什么 → 攻击者得到什么"，哪怕有前提。前提写进 `preconditions`。
- 只觉得"不够严谨"但说不出来利用方式的，不是候选。
- 同一处有多个独立成立的实例（三个路由共用一个没转义的渲染），一条断言，`instance` 区分。

## 基线板块

- 依赖：有已知漏洞的版本（对照锁文件和公开公告；不能联网就 deferred 并说明）；不再维护的、来源不明的、指向可变分支的 git 依赖。`kind: dependency`。
- 密钥与凭据：硬编码的密钥、令牌、密码、连接串，测试用的也记并注明；示例和注释里的真实凭据。`kind: secret`。
- 配置：调试开关、详细错误页、目录列举、宽松的 CORS 是否在生产配置里打开；容器以 root 运行、端口暴露、默认口令；哈希算法、会话 cookie 属性、上传限制这些安全缺省值。`kind: config`。

这三类不需要路径。

## 怎么记

每条一个 `finding.create`，`kind` 取自上下文的 `pack.findingKinds`；`identity.anchor` 描述失效之处的作用（`archive-extract-without-containment`）；`anchors` 指向链上的关键行。

查过没候选的板块 `disposition.set: no_issue`，理由写查了什么；按设计就不适用的 `not_applicable`；没查完的 `deferred`，理由写还差什么。
